Part 1 · Foundation

자료구조와 ADT: 왜 분리해서 보나?

Python 3.10의 built-in types 분류(수치형·시퀀스형·매핑형·집합형)를 기준으로 보면, 자료구조 선택은 단순 문법이 아니라 연산 의미를 선택하는 과정입니다. 또한 데이터 모델 관점에서 변수는 객체를 담는 상자가 아니라 이름 바인딩이므로, 같은 코드라도 참조 공유 여부에 따라 동작이 크게 달라집니다.

$$ \text{ADT} = \langle \mathcal{S}, \mathcal{O}, \mathcal{I} \rangle $$ \(\mathcal{S}\): 상태 공간, \(\mathcal{O}\): 연산 집합, \(\mathcal{I}\): 불변식

강의 전체 프레임: 문제를 ADT로 추상화한 뒤, 구현 구조를 선택하고 마지막에 정확성/복잡도/재현성을 검증합니다.

ADT (추상 자료형)

“무엇을 하는가”를 정의합니다. 예: Stack은 push/pop을 제공해야 한다.

Data Structure (구현)

“어떻게 하는가”를 정의합니다. 예: Stack을 list로 구현할지 deque로 구현할지 선택한다.

Part 1.1 · Theory

복잡도 이론: 점근 표기와 비용 모델

실행 시간은 기계/인터프리터/캐시 상태에 따라 달라지므로, 입력 크기 n에 대한 성장률로 알고리즘을 비교합니다. 자료구조 선택의 1차 기준은 상수항이 아니라 점근적 증가율입니다.

연구 코드에서 자주 혼동되는 지점은 “빠르다”의 의미입니다. 단일 입력의 절대 시간보다, 토큰 길이·배치 크기·스텝 수가 증가할 때 비용 곡선이 어떻게 변하는지가 더 중요합니다. 따라서 자료구조 비교는 동일한 연산 시퀀스와 동일한 입력 분포를 기준으로 점근 표기와 실측치를 함께 해석해야 합니다.

$$ T(n)\in O(g(n)) \iff \exists c>0,\ \exists n_0\ \text{s.t.}\ 0\le T(n)\le c\,g(n),\ \forall n\ge n_0 $$
표기의미해석
O(g(n))점근적 상한최악/상한 관점에서 비용이 g(n)을 넘지 않음
Ω(g(n))점근적 하한최소한 g(n)만큼은 필요함
Θ(g(n))점근적 동치상한·하한이 같은 차수

예: list.pop(0)는 요소 시프트로 Θ(n), dict.get은 평균 Θ(1)입니다. 같은 Python 코드라도 자료구조가 바뀌면 차수가 바뀝니다.

Part 1.2 · Amortized Analysis

상환 분석: 왜 append는 평균적으로 O(1)인가?

동적 배열(list)의 append는 개별 연산 기준으로는 최악 O(n)입니다. 그러나 연산열(sequence) 전체를 보면 총비용이 선형이므로 연산당 평균 비용은 상수입니다. 상환 분석은 바로 이 “연산열 수준 보장”을 제공하는 도구입니다.

분석 모델을 명확히 두겠습니다. 현재 길이를 m, 용량을 c라 하면, m < c인 append 비용은 1(쓰기), m = c이면 새 배열 할당 + 기존 원소 m개 복사 + 쓰기 1로 m+1입니다. 성장 정책은 c' = 2c로 가정합니다.

$$ \text{if }c_t = 2^t,\ \sum_{j=0}^{t-1}c_j = 2^t-1 \Rightarrow \text{total copy work before capacity }2^t\text{ is }<2^t $$
분석 축핵심 결론
Worst-case per op재할당 시점의 append는 O(n)
Total cost over n appends쓰기는 n, 누적 복사는 2n 미만, 따라서 총 O(n)
Amortized cost총 O(n)/n = O(1)
시스템 관점지연 스파이크는 존재하지만 장기 처리량(throughput)은 선형적으로 안정

가정의 역할

상환 O(1)은 “증가율이 1보다 큰 상수배 성장”과 “복사 비용이 원소 수에 비례”라는 모델 위에서 성립합니다. 성장 정책이 선형 증가이면 상환 O(1)이 깨집니다.

실전 시사점

append 중심 배치 누적에는 list가 유리합니다. 반면 앞단 삭제/삽입이 주연산이면 상환 분석 대상이 달라지므로 deque로 구조를 분리해야 합니다.

Part 1.2.1 · Proof

상환 O(1)의 엄밀한 증명: Aggregate / Accounting / Potential

정리(Theorem). 빈 동적 배열에 대해, 용량이 가득 찰 때마다 2배로 확장한다고 하자. n번의 append 총비용은 O(n)이며, 따라서 상환 비용은 O(1)이다.

1) Aggregate Method

$$ T(n)=n+\sum_{j=0}^{k-1}2^j,\ \text{where }2^k \le n < 2^{k+1} $$ $$ T(n) \le n + (2^k-1) < n+n = 2n $$

여기서 첫 항 n은 각 append의 쓰기 비용, 두 번째 항은 재할당 시 누적 복사 비용입니다. 결과적으로 T(n)/n < 2이므로 상환 비용은 상수입니다.

2) Accounting Method

각 append에 크레딧 3을 부과합니다. 실제 쓰기에 1을 즉시 지불하고 2를 적립합니다. 재할당 시 복사되는 각 원소는 과거에 적립한 크레딧 1개로 복사비를 지불할 수 있습니다.

모든 원소는 다음 재할당까지 충분한 크레딧을 보유하므로 적자가 발생하지 않습니다. 따라서 상환 비용은 상수(여기서는 3)로 상계됩니다.

3) Potential Method

잠재함수를 \Phi = 2m - c로 둡니다(m: 길이, c: 용량). 항상 \Phi \ge 0 (충분히 큰 단계에서)이며, 상환비용을 \hat{c}_i = c_i + \Phi_i - \Phi_{i-1}로 둡니다.

$$ \text{non-resize: }c_i=1,\ \Delta\Phi=2 \Rightarrow \hat{c}_i=3 $$ $$ \text{resize at }m=c:\ c_i=m+1,\ \Delta\Phi=2-m \Rightarrow \hat{c}_i=3 $$ $$ \therefore\ \forall i,\ \hat{c}_i \le 3 \Rightarrow \sum_{i=1}^n c_i \le \sum_{i=1}^n \hat{c}_i = O(n) $$
정책 변화상환 결과해석
확장비율 r > 1 상수append 상환 O(1)기하급수 확장으로 재할당 횟수 로그 수준
확장비율 r = 1 + 1/k 형태(거의 선형)상환 비용 증가 가능복사 누적이 선형보다 크게 증가할 수 있음
축소 정책까지 포함thrashing 가능성 검토 필요히스테리시스(예: 1/4 이하에서 축소) 필요
Part 1.3 · Hash Table Math

해시 테이블 이론: 로드 팩터와 기대 비용

딕셔너리의 평균 O(1)은 “무조건”이 아니라 해시 함수 분산성과 적절한 리사이즈 정책에 의존합니다.

핵심은 균등 해싱 가정입니다. 키가 버킷에 균일하게 분포된다는 가정이 깨지면 탐색 길이가 길어지고, 평균 O(1) 근사도 약해집니다. 따라서 키 설계(불변성, 동등성, 해시 일관성)는 단순 구현 문제가 아니라 성능 보장의 전제 조건입니다.

$$ \alpha=\frac{n}{m},\quad \mathbb{E}[\text{lookup}] \approx O(1+\alpha) $$
상태현상영향
α가 낮음충돌 감소조회/삽입이 안정적으로 빠름
α가 높음충돌 증가탐사 길이 증가, 캐시 비효율
리사이즈 발생재해싱 비용단기 스파이크, 장기 평균은 유지

“평균 O(1)” 표현은 가정(해시 분산/적대적 입력)을 함께 명시해야 의미가 정확해집니다.

Part 1.4 · CPython Memory Model

CPython 객체 모델과 메모리 오버헤드

파이썬 컨테이너는 원시 값 배열이 아니라 객체 포인터 배열을 저장합니다. 따라서 “원소 수”뿐 아니라 “원소 객체 자체의 오버헤드”를 함께 고려해야 메모리 사용량을 정확히 예측할 수 있습니다.

대학원 수준에서 중요한 포인트는 메모리 해석 단위를 “값”이 아니라 “객체 그래프”로 보는 것입니다. 예를 들어 같은 정수 10,000개라도 list[int], array, ndarray는 저장 모델이 달라 캐시 지역성(locality)과 순회 처리량이 크게 달라집니다. 즉 자료구조 선택은 시간복잡도뿐 아니라 메모리 계층 구조(L1/L2/cache miss)와도 직접 연결됩니다.

$$ M_{\text{total}} \approx M_{\text{container-header}} + M_{\text{pointer-array}} + \sum_{i=1}^{n}\left(M_{\text{obj-header},i}+M_{\text{payload},i}\right) $$

list는 값을 직접 저장하지 않고 객체 참조를 저장합니다. 대규모 데이터에서는 이 계층 구조가 메모리와 캐시 효율을 결정합니다.

import sys

nums: list[int] = list(range(10_000))
tu: tuple[int, ...] = tuple(range(10_000))
st: set[int] = set(range(10_000))

print("list bytes :", sys.getsizeof(nums))
print("tuple bytes:", sys.getsizeof(tu))
print("set bytes  :", sys.getsizeof(st))
print("one int    :", sys.getsizeof(0))
구조메모리 특성설계 시사점
list연속 포인터 배열 + 여유 용량순차 접근/끝 삽입 유리
dict/set해시 슬롯 + 엔트리 오버헤드 큼속도는 빠르나 메모리 비용 큼
tuple불변, 상대적으로 컴팩트키/레코드 표현에 유리

실무 지침: 수치 집약 루프는 Python 객체 컨테이너(list/dict/set) 안에서 직접 연산하지 말고, 가능한 한 배열/텐서 표현으로 일찍 변환해 연산 경로를 분리하세요.

print(a[0], a[-1])

리스트는 순서가 있는 가변 시퀀스이므로, “위치 기반 접근”이 핵심입니다. 수학적으로는 함수 f: {0,...,n-1} → ObjectRef 로 모델링할 수 있고, 인덱스 연산은 f(i) 조회에 해당합니다.

$$ \text{update at }i:\quad f'(j)= \begin{cases} x & (j=i) \\ f(j) & (j\neq i) \end{cases} $$

실전에서는 리스트를 “작은 배열”로 보는 습관이 중요합니다. 앞쪽 삽입/삭제는 내부 시프트를 유발하고, 슬라이싱은 복사를 유발합니다. 즉, 리스트는 범용 컨테이너지만 모든 연산에 균등하게 좋은 자료구조는 아니며, 연산 패턴(앞/뒤/중간, 조회/갱신 비율)에 따라 선택되어야 합니다. 시퀀스 배치 구성, 길이별 버킷팅, 샘플 셔플 버퍼처럼 순서 중심 연산에서는 list가 기준 구조가 됩니다.

핵심 관찰

  • 음수 인덱스: 뒤에서 접근
  • 슬라이싱은 새 리스트 생성
  • append와 extend 의미 차이

빈발 오류 사례

  • [[0]*3]*4의 참조 공유 버그
  • remove 반복 중 인덱스 꼬임
  • pop(0)를 큐처럼 사용 (비효율)
$$ k=j-i,\quad \text{time}(a[i:j])=\Theta(k),\quad \text{space}(a[i:j])=\Theta(k) $$
Part 2.1 · List Internals

리스트 내부 구현과 성능

리스트는 C 레벨에서 동적 배열로 구현되며, 배열에는 객체 자체가 아니라 객체 참조가 저장됩니다.

$$ T_{\text{insert at }i}(n)=\Theta(n-i),\qquad T_{\text{delete at }i}(n)=\Theta(n-i) $$

이 설계 덕분에 리스트는 이질적인 타입을 한 컨테이너에 담을 수 있습니다. 반면 참조 간접(indirection)과 객체 헤더 오버헤드가 존재하므로, 대규모 수치 계산에서는 메모리 지역성(locality)과 캐시 효율이 병목이 될 수 있습니다. 따라서 수치 집약 작업에서는 배열 라이브러리와의 역할 분리가 필요합니다.

$$\text{amortized append} = O(1)\quad(\text{occasional resize} + \text{frequent constant-time writes})$$
연산복잡도설명
a[i]O(1)오프셋 계산으로 즉시 접근
append(x)Amortized O(1)오버할당으로 재할당 빈도 감소
insert(0,x)O(n)전체 시프트
pop(0)O(n)앞 원소 제거 후 당김
sort()O(n log n)Timsort(부분 정렬 데이터에 강함)

Part 2.3 · List Deep Notes

리스트 연산 상세 정리: 문법, 의미, 주의사항

아래 내용은 강의 중 빠르게 참조할 수 있는 “리스트 운영 매뉴얼”입니다. 표면 문법뿐 아니라 언제 비용이 커지는지, 어떤 메서드가 제자리(in-place)인지, 새 객체를 반환하는지를 같이 봐야 합니다.

Part 3.1 · Dict Internals

딕셔너리 내부: 해시, 충돌, 키 설계

딕셔너리는 해시 테이블입니다. 핵심은 좋은 키와 충돌 관리입니다.

실전에서는 평균 O(1)만 외우면 부족합니다. 충돌이 늘어나는 데이터 분포, 해시 일관성이 깨진 사용자 정의 객체, 과도한 리사이즈가 동시에 발생하면 tail latency가 크게 흔들립니다. 따라서 키 설계 단계에서 불변성·동등성·해시 일관성을 명시하고, 조회 실패 정책을 함께 문서화해야 합니다.

$$ k_1 = k_2 \Rightarrow h(k_1)=h(k_2)\quad\text{(required)} $$ $$ h(k_1)=h(k_2) \not\Rightarrow k_1=k_2\quad\text{(collision allowed)} $$

딕셔너리 성능은 키 설계 품질에 크게 의존합니다. 해시 충돌·조회 정책·키 불변성은 반드시 함께 설계해야 합니다.

# hashable 조건: 불변 + __hash__ 구현
print(hash((1, 2, 3)))
# print(hash([1, 2, 3]))  # TypeError

# 사용자 정의 키
from dataclasses import dataclass

@dataclass(frozen=True)
class Node:
    id: int
    label: str

d: dict[Node, float] = {Node(1, "A"): 3.14}
print(d[Node(1, "A")])
# 실험 캐시 키 설계 예시 (튜플 키 권장)
metrics_cache: dict[tuple[str, int, float], dict[str, float]] = {}
cfg_key: tuple[str, int, float] = ("bert-base", 32, 3e-5)
metrics_cache[cfg_key] = {"val_f1": 0.913, "val_loss": 0.224}

# 키가 list면 TypeError, 가변 구조라 재현성 있는 조회가 어렵다.

리스크증상예방 규칙
가변 객체 키 사용삽입 후 조회 실패/불안정키 타입은 불변 객체로 제한
__eq__/__hash__ 불일치동등 객체가 다른 슬롯에 저장동등성 계약을 테스트로 강제
적대적 충돌 분포조회 지연 급증키 정규화 + 분포 점검 벤치마크
누락 키 처리 정책 부재간헐적 KeyError 또는 silent defaultd[k]/get 사용 규칙 분리
$$ \text{Key design rule: immutable key } \land \left(a=b \Rightarrow h(a)=h(b)\right) $$ \(\texttt{\_\_eq\_\_}\)와 \(\texttt{\_\_hash\_\_}\)는 항상 일관되게 설계

주의: 가변 객체를 키로 사용하거나, hash/eq 불일치가 있으면 치명적 버그가 발생합니다.

Part 3.10 · Tuple Design

Tuple 상세: 불변 시퀀스와 구조적 데이터 표현

tuple은 “값 객체(value object)” 모델에 적합합니다. 실험 파라미터, 다중 키, 좌표값처럼 변경되면 안 되는 구조를 표현할 때 의미적으로도 명확합니다.

특히 튜플은 “상태가 변하면 다른 객체가 되어야 하는” 문제에서 유용합니다. 예를 들어 캐시 키, 그래프 좌표, 파이프라인 스냅샷과 같이 동일성(identity)보다 값(value) 의미가 중요한 경우, 튜플을 사용하면 의도치 않은 변경을 구조적으로 차단할 수 있습니다.

Part 3.11 · Set/Tuple Design Rationale

set과 tuple의 선택 기준: 의미 모델 중심

구조 선택은 단순 성능 비교가 아니라 데이터 의미를 보존하는 문제입니다. tuple은 “순서 있는 불변 레코드”, set은 “순서 없는 원소 집합”으로 의미가 다르므로, 표현 자체가 검증 규칙을 결정합니다.

tuple이 적합한 경우

  • 실험 파라미터처럼 키로 사용해야 하는 경우
  • 순서가 의미를 가지는 경우
  • 갱신을 금지해야 하는 경우

set이 적합한 경우

  • 중복 제거가 필요한 경우
  • 멤버십 테스트가 지배적인 경우
  • 집합 연산(교집합/차집합)이 핵심인 경우
$$ \text{representation} \Rightarrow \text{valid operations} \Rightarrow \text{proof obligations} $$

즉, 표현 선택이 이후 알고리즘과 검증의 범위를 규정합니다. 자료구조 선택 단계에서 의미 모델을 먼저 확정해야 구현 단계의 시행착오를 줄일 수 있습니다.

Part 4.1 · Implementations

ADT 구현 예시: 타입 힌트 + 예외 설계

구현 예시는 “API 계약 + 예외 정책 + 정렬 가능 데이터 모델”을 한 번에 보여주는 최소 단위입니다. 핵심은 기능 추가보다 경계 조건을 코드에 명시하는 것입니다.

from dataclasses import dataclass
from typing import Generic, TypeVar

T = TypeVar("T")

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._data: list[T] = []

    def push(self, x: T) -> None:
        self._data.append(x)

    def pop(self) -> T:
        if not self._data:
            raise IndexError("pop from empty stack")
        return self._data.pop()

@dataclass(order=True)
class Task:
    priority: int
    name: str

s = Stack[int]()
s.push(10); s.push(20)
print("stack pop:", s.pop())

tasks: list[Task] = [Task(2, "train"), Task(1, "eval")]
print("sorted tasks:", sorted(tasks))

설계 포인트

  • 빈 스택 pop은 즉시 예외로 실패를 명시
  • Generic[T]로 자료형 계약을 API에 반영
  • @dataclass(order=True)로 정렬 규칙 내장

리뷰 체크리스트

  • precondition/postcondition이 코드에 드러나는가?
  • 예외 메시지가 디버깅 가능한가?
  • 테스트에서 빈 구조/단일 원소 경계를 검증했는가?

“동작한다”보다 “경계 조건과 타입 안정성을 포함해 설계했는가”가 핵심 평가 기준입니다.

Part 4.3 · Formal ADT Spec

형식 명세와 정당성: ADT를 증명 가능하게 설계하기

구현 코드보다 먼저 연산 명세를 정의해야 테스트/검증/최적화가 일관성을 유지할 수 있습니다.

$$ \text{Stack ADT}:\ S=\text{sequence},\quad \operatorname{push}(x):S'=S\circ[x] $$ $$ \operatorname{pop}():\ |S|>0,\ \text{return }\operatorname{last}(S),\ S'=\operatorname{prefix}(S,|S|-1) $$ 
from typing import Generic, TypeVar

T = TypeVar("T")

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._data: list[T] = []

    def push(self, x: T) -> None:
        before = len(self._data)
        self._data.append(x)
        assert len(self._data) == before + 1

    def pop(self) -> T:
        assert len(self._data) > 0, "precondition: non-empty"
        x = self._data.pop()
        return x

s = Stack[int]()
s.push(1); s.push(2)
print(s.pop(), s.pop())

연구/산업 공통으로, “assert는 명세의 실행 가능한 형태”입니다. 핵심 불변식을 코드에 명시하면 반례를 조기에 발견할 수 있습니다.

Part 4.4 · DS Selection Framework

자료구조 선택 프레임워크: 비용 함수 기반 의사결정

실험 파이프라인에서 가장 어려운 결정 중 하나는 “어떤 자료구조를 선택할지”입니다. 아래처럼 연산 비율과 메모리 제약을 비용 함수로 모델링하면 선택 근거를 명확히 제시할 수 있습니다.

대학원 연구에서는 성능만으로 선택하면 부족합니다. 실패 확률(예: 키 누락, 상태 공유 오염), 재현성 요구(순서 안정성), 디버깅 비용(관측 가능성)을 함께 비용 항으로 넣어야 실험 반복 시 품질 편차를 줄일 수 있습니다.

$$ C(D)=\sum_{op\in\mathcal{O}} w_{op}\,T_D(op) + \lambda M_D $$ \(w_{op}\): 연산 빈도 가중치, \(T_D(op)\): 자료구조 \(D\)에서의 비용, \(M_D\): 메모리 비용
$$ C'(D)=C(D)+\mu R_D+\nu G_D $$ \(R_D\): 실패 리스크, \(G_D\): 가독성/검증 비용. 즉 “빠른 구조”와 “검증 가능한 구조”의 균형이 필요합니다.

같은 문제라도 비용 항 가중치(\(w,\lambda,\mu,\nu\))에 따라 최적 자료구조가 달라집니다. 논문/프로젝트 보고서에는 이 가정이 반드시 명시되어야 합니다.

Part 5 · Complexity Lab

실험으로 검증하는 성능: 이론 vs 실제

같은 O-표기라도 데이터 크기와 연산 위치가 다르면 체감 속도는 크게 달라집니다. 아래 실험은 “앞쪽 삭제”라는 특정 연산이 구조 선택에 얼마나 큰 차이를 만드는지 보여줍니다.

연구 코드에서는 “한 번 더 빨라졌다”가 아니라 “입력 분포가 바뀌어도 안정적으로 빠른가”가 핵심입니다. 따라서 실험은 단일 평균값이 아닌 분포(최소/최대/분산)와 함께 보고, 코드 경로(연산 위치/캐시 워밍/객체 생성량)를 함께 기록해야 해석 오류를 줄일 수 있습니다.

import time
from collections import deque

N: int = 80_000
arr: list[int] = list(range(N))
q: deque[int] = deque(range(N))

start = time.perf_counter()
for _ in range(15_000):
    arr.pop(0)
list_time: float = time.perf_counter() - start

start = time.perf_counter()
for _ in range(15_000):
    q.popleft()
deque_time: float = time.perf_counter() - start

print(f"list.pop(0): {list_time:.4f}s")
print(f"deque.popleft(): {deque_time:.4f}s")

절대 시간값보다 연산 패턴별 상대 비용 차이를 읽는 것이 중요합니다. 앞삭제가 지배적이면 list 대신 deque가 구조적으로 유리합니다.

$$ \text{Observed time} \approx f(n)\cdot c_{\text{impl}}\cdot c_{\text{hardware}} $$ Big-O는 증가율을 설명하고, 실제 성능은 상수항/캐시/런타임 구현체 영향을 함께 측정해야 합니다.
관찰 포인트해석
list.pop(0) 증가폭원소 시프트 때문에 N 증가 시 선형적으로 악화
deque.popleft() 안정성양끝 연산 O(1)이라 반복 횟수에 비례해 완만히 증가
실험 재현성동일 입력 생성, warm-up, 반복 측정으로 편차 통제

해석 규칙: “이론과 측정이 다르다”가 아니라 “이론은 증가율, 측정은 상수항과 시스템 효과를 포함한다”로 분리해 읽어야 정확합니다.

Part 6 · Pythonic High-Level

심화 문법과 자료구조 결합

고급 문법은 “코드를 단축하는 것”이 목적이 아니라, 자료구조의 형태를 코드에 명시적으로 반영해 오류 가능성을 줄이는 데 목적이 있습니다.

특히 Python 3.10의 패턴 매칭은 중첩 자료구조 분기를 선언적으로 표현할 수 있어 파싱/디스패치 코드의 의도를 크게 개선합니다. 다만 분기 규칙이 암묵적으로 늘어나면 디버깅 난이도가 올라가므로, “분기 표(입력 패턴 → 출력 동작)”를 함께 유지하는 것이 안전합니다.

    match x:
        case []:
            return "empty"
        case [a, b]:
            return f"pair({a},{b})"
        case {"type": t, "payload": p}:
            return f"msg:{t}"
        case _:
            return "other"

from collections import deque

def bfs(graph: dict[str, list[str]], start: str) -> list[str]:
    q: deque[str]
    seen: set[str]
    q, seen = deque([start]), {start}
    order: list[str] = []
    while q:
      v = q.popleft()
      order.append(v)
      for nxt in graph[v]:
        if nxt not in seen:
          seen.add(nxt); q.append(nxt)
    return order

g: dict[str, list[str]] = {"n0": ["n1", "n2"], "n1": ["n3"], "n2": [], "n3": []}
print(bfs(g, "n0"))

def has_dup_k(arr: list[int], k: int) -> bool:
    last: dict[int, int] = {}
    for i, x in enumerate(arr):
      if x in last and i - last[x] <= k:
        return True
      last[x] = i
    return False

import copy

a: list[list[int]] = [[1, 2], [3, 4]]
b: list[list[int]] = a[:]                # shallow copy
c: list[list[int]] = copy.deepcopy(a)    # deep copy

얕은 복사는 “바깥 컨테이너만 새로 만들고 내부 객체 참조는 공유”합니다. 따라서 코드가 정상 동작하는 것처럼 보이다가, 후반 단계에서 내부 상태 오염이 발견되는 형태의 결함을 만들기 쉽습니다.

성능 관점

  • 깊은 복사는 안전하지만 비용이 큼
  • 불변 객체 중심 설계는 디버깅/동시성에 유리

설계 관점

  • 함수 경계에서 입력 변경 여부를 명시
  • 공유 상태가 필요하면 문서화 + 테스트 강화

얕은 복사 버그 패턴 2선 (실패/정상 예제)

import copy

# 패턴 1) 리스트 슬라이싱/ copy()는 '얕은 복사'
src: list[list[int]] = [[1, 2], [3, 4]]
shallow: list[list[int]] = src[:]                 # 또는 src.copy()
deep: list[list[int]] = copy.deepcopy(src)

shallow[0].append(99)
print("src:", src)      # [[1,2,99],[3,4]]  <- 영향 받음

# 패턴 2) dict.copy()도 얕은 복사

d2["a"]["x"] = 999
print(d1["a"]["x"])     # 999 (원본 오염)

# 3) 함수에서 원본 보호 패턴
def safe_transform(items: list[str]) -> list[str]:
    local: list[str] = items.copy()         # 1차원이면 충분
    local.append("new")
    return local

base: list[str] = ["A", "B"]
out: list[str] = safe_transform(base)
print(base, out)       # 원본 유지

def safe_nested(d: dict[str, dict[str, float]]) -> dict[str, dict[str, float]]:
    local: dict[str, dict[str, float]] = copy.deepcopy(d)
    local["cfg"]["lr"] *= 10
    return local

Part 6.4 · Memory Management

파이썬 메모리 관리: 참조 카운트 + 사이클 GC

파이썬(CPython)은 기본적으로 참조 카운팅(reference counting)으로 객체 생명주기를 관리하고, 순환 참조는 세대별 가비지 컬렉터가 처리합니다.

이중 구조를 이해하면 메모리 누수 분석이 쉬워집니다. 단순 객체는 참조 카운트가 0이 되는 즉시 해제되지만, 순환 참조 구조는 카운트만으로 해제되지 않습니다. 따라서 장기 실행 프로세스에서는 cycle을 만들기 쉬운 객체 그래프를 점검하고, 필요 시 약한 참조 또는 명시적 해제 전략을 고려해야 합니다.

$$ \text{alive}(o)\iff \operatorname{refcount}(o)>0,\qquad \text{cycle garbage requires tracing GC} $$ 
import gc

class Node:
    def __init__(self) -> None:
        self.ref: Node | None = None

a: Node = Node()
b: Node = Node()
a.ref = b; b.ref = a   # cycle

del a; del b
print("before collect:", gc.get_count())
gc.collect()
print("after collect:", gc.get_count())
# 딥러닝 루프에서 그래프/텐서 참조 누수 방지 패턴
loss_history: list[float] = []
for step_loss in [0.92, 0.71, 0.55]:
    # 실제 torch 코드에서는 loss.item() 값만 보관하는 습관이 중요
    loss_history.append(float(step_loss))
print(loss_history)

메모리 관점에서 list/dict/set은 객체 참조를 저장하므로, 원소 수가 늘면 컨테이너 오버헤드 + 객체 오버헤드가 동시에 증가합니다. 대규모 파이프라인에서는 구조 선택뿐 아니라 데이터 표현(정수/문자열/객체)을 함께 설계해야 합니다.

Part 6.5 · Logical Correctness

논리적 정확성: 불변식(invariant)과 경계조건

코드 리뷰에서는 “돌아간다”보다 “왜 항상 맞는가”를 증명 가능한 형태로 설명해야 합니다. 이를 위해 불변식을 명시하고 각 연산이 불변식을 보존하는지 점검합니다.

예: Stack 불변식

  • size == len(data)
  • top은 마지막 삽입 원소
  • push/pop 후에도 LIFO 유지

검증 체크리스트

  • 빈 구조에서 연산 예외 처리
  • 중복 키/누락 키 시 정책 일관성
  • 얕은 복사/깊은 복사 부작용 여부
$$ \forall t\ge 0:\ I(S_t)\ \land\ \text{op preserves }I\ \Rightarrow\ I(S_{t+1}) $$ 
def push(stack: list[int], x: int) -> None:
    before = len(stack)
    stack.append(x)
    assert len(stack) == before + 1   # invariant check

def pop_safe(stack: list[int]) -> int | None:
    if not stack:
        return None
    return stack.pop()

s: list[int] = []
push(s, 10); push(s, 20)
print(pop_safe(s), pop_safe(s), pop_safe(s))
Part 6.6 · Concurrency & Immutability

동시성과 불변 데이터: 안전한 공유 상태 설계

병렬/비동기 환경에서는 자료구조 선택이 곧 동시성 안전성입니다. 공유 상태를 줄이고 불변 구조를 우선하면 race condition 가능성이 크게 감소합니다. 데이터 로더 워커, 비동기 전처리 태스크, 추론 요청 큐를 동시에 운영할수록 이 원칙의 효과가 커집니다.

불변 tuple/dataclass 공유레이스 위험 감소, 스냅샷 추적 용이갱신 시 새 객체 생성 비용
복사 후 로컬 수정모듈 경계 독립성 확보깊은 복사 비용/지연 고려 필요
락/큐 기반 동기화일관성 강제 가능병렬성 감소 및 교착 상태 관리 필요

동시성 안전성은 락 하나로 끝나지 않습니다. 공유 상태를 줄이고 immutable 스냅샷/메시지 전달 중심으로 구조를 바꾸는 것이 근본 해법입니다.

CPython GIL이 있다고 해서 논리적 race가 사라지지 않습니다. 연산의 원자성, 데이터 불변성, 동기화 경계를 별도로 설계해야 합니다.

Part 7 · Core Semantics I

참조, 변이, 복사를 하나의 모델로 통합해 이해하기

여기부터는 앞에서 배운 list/dict/set/tuple 연산을 단편 팁이 아니라 하나의 의미론으로 묶어 설명합니다. 핵심은 “이름-객체 바인딩”, “가변성”, “복사 깊이”가 실제 코드 동작을 어떻게 결정하는지입니다.

개념 1: 함수 기본값의 객체 수명

def f(x: int, cache: list[int] = []) -> list[int]:
    cache.append(x)
    return cache

print(f(1))
print(f(2))  # 호출 간 상태 공유

기본 인자는 함수 정의 시 1회 평가됩니다. 따라서 mutable 기본값은 호출 간 상태를 공유합니다.

개념 2: 얕은 복사와 중첩 참조

a: list[list[int]] = [[1], [2]]
b: list[list[int]] = a.copy()
b[0].append(99)
print(a)  # 영향 받음

얕은 복사는 바깥 컨테이너만 분리합니다. 내부 객체 공유를 끊으려면 deep copy 또는 불변 구조화가 필요합니다.

개념 3: 순회 중 변경과 불변식 붕괴

arr: list[int] = [1, 2, 3, 4, 5, 6]
for x in arr:
    if x % 2 == 0:
        arr.remove(x)
print(arr)  # 일부 값이 건너뛰어짐

순회 인덱스와 컨테이너 구조가 동시에 변해 루프 불변식이 깨집니다. 필터 재구성이 정석입니다.

설계 규칙으로 환원

def f(x: int, cache: list[int] | None = None) -> list[int]:
    if cache is None:
        cache = []
    cache.append(x)
    return cache

arr: list[int] = [1, 2, 3, 4, 5, 6]
arr = [x for x in arr if x % 2 == 1]

검증 체크포인트

  • 동일 함수를 2회 이상 호출해 상태 누수 확인
  • 중첩 구조 복사 후 원본/사본 동시 검증
  • 순회 중 변경 로직은 입력 길이 0/1/짝수/홀수 모두 테스트

Part 7.3 · Iteration & Ordering Semantics

수치 연산, 이터레이터, 순서 안정성을 같은 축으로 이해하기

이 파트의 목표는 “동작은 되는데 결과가 틀리는 코드”를 줄이는 것입니다. 연산 의미(연결 vs 원소별 연산), 소비 모델(1회 vs 재사용), 순서 보존(보장 vs 비보장)을 동시에 봐야 합니다.

list vs ndarray/tensor

import numpy as np

x: list[int] = [1, 2, 3]
y: list[int] = [4, 5, 6]
print("list + list:", x + y)  # 연결

xn: np.ndarray = np.array(x)
yn: np.ndarray = np.array(y)
print("ndarray + ndarray:", xn + yn)  # 원소별 합

핵심: 자료형이 바뀌면 연산 의미가 바뀝니다. 벡터 연산은 list가 아닌 배열/텐서 문맥에서 정의해야 합니다.

data = map(int, ["1", "2", "3"])

Part 7.4 · State & Lifecycle Semantics

상태 공유와 메모리 생명주기를 코드 레벨에서 통제하기

여기서는 “왜 메모리가 늘고 결과가 달라지는가”를 객체 생명주기 관점에서 설명합니다. 핵심은 참조가 남아 있는 한 객체는 살아 있고, 클로저/기본값/in-place 연산이 이 참조를 길게 유지한다는 점입니다.

default mutable argument

def add_layer(layer: int, layers: list[int] | None = None) -> list[int]:
    if layers is None:
        layers = []
    layers.append(layer)
    return layers

in-place + reference 오염

a: list[int] = [1, 2, 3]
b = a          # reference 공유
b.append(4)
print(a)       # [1,2,3,4]

c = a.copy()   # 독립 객체
c.append(5)

Tensor graph 유지로 메모리 증가

losses = []

for _ in range(3):
    loss = model(batch)         # Tensor
    losses.append(loss.item())  # 또는 loss.detach()

핵심: 기록용 컨테이너에는 계산 그래프가 아닌 값(snapshot)만 저장해야 메모리 생명주기가 안정됩니다.

late binding (lambda)

funcs = [lambda x, i=i: x * i for i in range(5)]
print(funcs[0](2))  # 0
print(funcs[4](2))  # 8

핵심: 클로저는 변수 참조를 잡기 때문에, 루프 변수는 기본 인자 캡처로 스냅샷화해야 합니다.
