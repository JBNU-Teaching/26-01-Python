Part 1 · Reorganization

재구성 원리: iterator → generator → list → class

강의 순서는 개념적 의존 관계를 기준으로 조직된다. class를 먼저 제시하면 객체 문법은 드러나지만, 그 객체가 구현하는 프로토콜과 실행 의미론은 뒤로 밀리게 된다.

iterator를 출발점으로 두면 Python 반복의 최소 계약이 먼저 드러난다. generator는 그 계약을 구현하는 실행 전략으로 배치되고, list는 계산 결과를 eager하게 고정하는 sequence로 해석된다. class는 마지막에 이 세 층을 API, 불변식, 타입 계약의 수준에서 통합하는 장치로 배치된다.

  • 프로토콜 우선 : 반복과 순회는 저장 구조보다 먼저 정의되는 계약으로 다루어진다.
  • 실행 전략 분리 : generator는 iterator 계약을 실현하는 구체적 메커니즘으로 배치된다.
  • 설계 통합 : class는 앞선 층을 도메인 API와 객체 정책으로 조직하는 최종 층이다.
$$\text{Protocol} \rightarrow \text{Execution Strategy} \rightarrow \text{Materialization} \rightarrow \text{Object Design}$$
강의 구조는 문법 항목의 나열이 아니라 추상화 계층의 전개로 구성된다. 프로토콜, 실행, 저장, 설계의 순서를 유지하는 것이 전체 의미론을 가장 안정적으로 드러낸다.

Part 4 · Iterator First

Iterator를 출발점으로 두는 이유

Python 반복의 최소 의미 단위는 list가 아니라 iterator protocol이다. 반복을 sequence의 부속 기능으로 해석하면 언어의 실제 실행 모델이 가려진다.

Python의 다수 내장 함수와 문법은 길이, 인덱싱, 전체 메모리 적재를 요구하지 않는다. 중심 질문은 다음 원소를 계속 생산할 수 있는가에 있다. 이 조건만 충족되면 sequence가 아니어도 상당수 연산이 성립한다.

  • 생산 중심 : 핵심 질문은 데이터를 보유하는가가 아니라 다음 값을 낼 수 있는가에 있다.
  • 메모리 독립성 : 전체 적재 없이도 반복이 성립하므로 스트림 처리가 가능하다.
  • 언어 일관성 : 같은 계약으로 list, file, generator, 사용자 정의 객체를 함께 다룬다.
$$\text{Iteration semantics} = \text{next value production} + \text{termination contract}$$
Sequence 중심 사고는 데이터 보유 구조를 먼저 본다. Iterator 중심 사고는 데이터 생산 과정을 먼저 본다.
Part 5 · Data Model

Python 데이터 모델에서 iteration이 차지하는 위치

Python 문법은 객체를 직접 다루기보다, 객체가 구현한 프로토콜을 통해 의미를 얻는다. iteration 역시 그중 하나이며, for 문은 특별한 list 문법이 아니라 iterator protocol 위에 놓인 고수준 구문으로 해석된다.

  • 객체 층 : 상태와 정체성은 객체 자체가 보유한다.
  • 프로토콜 층 : special method가 문법이 이해할 계약을 제공한다.
  • 문법 층 : 사용자 문법은 결국 protocol 해석 결과로 작동한다.
$$\text{syntax meaning} = \text{object protocol interpretation}$$
Part 6 · Protocol

Iterator protocol의 최소 규약

$$\text{iterator} \iff \text{has } \_\_iter\_\_() \text{ returning self and } \_\_next\_\_()$$

iter(obj)

객체에게 순회를 시작할 수 있는 객체를 요청한다. iterable은 보통 새 iterator를 반환하고, iterator는 자기 자신을 반환한다.

next(it)

iterator에게 다음 원소를 요청한다. 더 이상 줄 값이 없으면 StopIteration을 발생시킨다.

이 규약은 작지만 표현력이 크다. 값 하나를 산출하는 계약만 지키면 list, 파일, 데이터베이스 커서, 네트워크 스트림을 동일한 추상화로 다룰 수 있다.

  • __iter__ : 순회 시작점을 제공한다. iterable은 보통 새 iterator를 반환하고, iterator는 자기 자신을 반환한다.
  • __next__ : 상태를 전진시키며 다음 값을 반환한다. 따라서 iterator는 본질적으로 상태 기계다.
  • StopIteration : 단순 오류가 아니라 정상 종료 신호다. 반복 문법 전체가 이 예외를 전제로 작동한다.
Part 7 · Desugaring

for 문은 내부적으로 무엇을 하는가

표면 문법

for x in data:
    body(x)

개념적 전개

_it = iter(data)
while True:
    try:
        x = next(_it)
    except StopIteration:
        break
    body(x)

이 전개는 반복이 sequence에 귀속된 개념이 아니라는 사실을 보여 준다. data는 길이가 없어도 되고, 인덱싱을 지원하지 않아도 되며, 무한할 수도 있다. 필요한 것은 오직 다음 값을 요청할 수 있는 계약뿐이다.

대규모 데이터 파이프라인이나 streaming inference 시스템에서는 전체 데이터를 list로 가정하는 모델이 성립하지 않는다. 반복 의미론을 sequence보다 더 낮은 층에서 이해해야 하는 이유가 여기에 있다.

  • 길이 비필수 : 반복은 len() 가능성과 독립적이다.
  • 인덱싱 비필수 : 순회는 순차 접근 계약만 필요로 한다.
  • 무한 구조 허용 : 종료 불확정 스트림도 protocol 수준에서는 반복 대상이 될 수 있다.
$$\texttt{for }x\texttt{ in }y \;\equiv\; \texttt{iter}(y) \;\circ\; \texttt{next}(\cdot) \;\circ\; \texttt{StopIteration handling}$$

이 구분을 흐리게 다루면 API 설계의 계약이 붕괴한다. 함수가 iterable을 기대하는지 iterator를 기대하는지 문서화하지 않으면, 재사용 가능한 데이터셋과 일회성 스트림이 동일한 타입처럼 오해된다.

가장 흔한 오류는 iterator를 재순회 가능한 데이터로 오해하여 두 번째 소비에서 빈 결과를 얻는 형태로 나타난다.
  • iterable : 반복을 시작할 수 있는 객체이며 보통 새 iterator를 제공한다.
  • iterator : 현재 순회 위치를 내부 상태로 보유하는 소모성 객체다.
  • sequence : 반복 가능성 외에도 길이, 인덱싱, 종종 슬라이싱을 제공하는 더 강한 추상화다.
$$\text{Iterator} \subset \text{Iterable},\qquad \text{Sequence} \subset \text{Iterable},\qquad \text{Iterator} \neq \text{Sequence}$$
Part 9 · Termination

왜 종료는 특별 값이 아니라 StopIteration 예외인가

종료를 값이 아니라 예외로 표현하는 선택은 iteration 의미론의 핵심 결정이다.

종료를 None 같은 특별 값으로 표현했다면 그 값은 정상 데이터로 사용할 수 없게 된다. 예외 기반 종료는 데이터 영역과 종료 신호를 분리하며, 그 결과 None, 0, 빈 문자열, 빈 리스트도 정상 원소가 될 수 있다.

it = iter([None, 0, "", []])
print(list(it))

iteration은 값 생산과 종료 통지를 분리하는 프로토콜이다. 이 분리는 generator의 return 값, yield from 위임, async iteration 종료 규칙으로 이어진다.

  • 데이터 보존 : None이나 빈 문자열도 정상 데이터로 유지된다.
  • 제어 흐름 분리 : 값 영역과 종료 신호가 분리되어 언어 차원의 반복 제어가 단순해진다.
  • 고급 문법 연결 : generator의 return, yield from, async iteration도 모두 이 종료 모델 위에서 설명된다.
$$\text{termination} = \text{exception channel},\qquad \text{data} \cap \text{termination signal} = \varnothing$$
Part 10 · Rare Syntax

iter(callable, sentinel) 문법은 왜 존재하는가

from functools import partial

with open("binary.log", "rb") as f:
    for chunk in iter(partial(f.read, 4096), b""):
        process(chunk)

이 문법은 callable을 반복 호출하여 sentinel이 나올 때까지 iterator를 구성한다. 즉, 종료값이 명확한 pull-based API를 iterator protocol로 감싸는 적응기 역할을 수행한다.

파일 블록 읽기, 장비 데이터 폴링, 외부 C 라이브러리 래핑처럼 반복 호출이 자연스러운 영역에서 특히 효과적이다. while True와 break 중심 제어를 더 선언적인 순회 표현으로 치환한다.

  • 적응기 : 반복 호출형 API를 iterator 소비자와 연결한다.
  • 종료 명시성 : sentinel이 종료 조건을 값 수준에서 분명히 제공한다.
  • 제어 단순화 : 저수준 루프를 protocol 기반 순회로 치환한다.
$$\texttt{iter}(f, s) = f(), f(), \ldots \text{ until } f() = s$$

Part 12 · Live Lab

직접 구현해 보는 커스텀 iterator

다음 코드는 짝수만 순회하는 컨테이너와 iterator를 분리하여 구현한 예시이다. 컨테이너와 순회 상태를 분리하는 구조는 재순회 가능성과 소모성 상태를 동시에 설명하는 데 적합하다.

class EvenNumbers:
    def __init__(self, start: int, stop: int):
        self.start = start if start % 2 == 0 else start + 1
        self.stop = stop

    def __iter__(self):
        return EvenNumbersIterator(self.start, self.stop)


class EvenNumbersIterator:
    def __init__(self, current: int, stop: int):
        self.current = current
        self.stop = stop

    def __iter__(self):
        return self

    def __next__(self):
        if self.current >= self.stop:
            raise StopIteration
        value = self.current
        self.current += 2
        return value


data = EvenNumbers(3, 15)
print(list(data))
print(list(data))

EvenNumbers는 재순회 가능한 iterable이다. list(data)를 두 번 호출해도 동일한 결과가 나오는 이유는 내부에서 매번 새로운 EvenNumbersIterator를 생성하기 때문이다.

  • 컨테이너 : 반복 정책과 입력 범위를 보존하되 순회 상태는 저장하지 않는다.
  • iterator : 현재 위치와 종료 조건을 가지고 실제 상태 전이를 담당한다.
  • 재순회성 : __iter__가 새 iterator를 반환해야 동일 결과가 재현된다.
$$\text{reiterable container} \Rightarrow \forall k,\ \texttt{iter(obj)}_k \text{ are independent iterators}$$

특히 데이터 과학과 머신러닝 코드에서는 이 구분이 치명적이다. 학습 데이터셋은 보통 iterable이어야 하고, 배치 생산기나 네트워크 스트림은 iterator일 가능성이 높다. 이 둘을 혼동하면 두 번째 epoch부터 데이터가 사라지는 버그가 쉽게 발생한다.

  • epoch 요구 : 학습 데이터셋은 매 epoch 새 순회를 시작할 수 있어야 한다.
  • 실시간 소모성 : 로그 tail이나 네트워크 스트림은 지나간 데이터를 다시 주지 못한다.
  • API 명시성 : 재순회 가능 여부는 타입과 문서에서 분명히 드러나야 한다.

        if "loss" in line:
            print(line.rstrip())

파일 객체는 sequence가 아니다. 인덱싱이 없고, 길이가 사전에 결정되지 않을 수 있으며, 전체 내용을 메모리에 적재하지 않는다. 그럼에도 for 문과 직접 결합된다. 이유는 iterator protocol을 구현하기 때문이다.

이 사례는 Python 반복 모델이 대용량 데이터 처리에 유리한 이유를 보여 준다. 반복 가능한 객체의 범위를 sequence보다 넓게 잡았기 때문에, 메모리 친화적이고 I/O 친화적인 설계가 가능하다.

  • I/O 친화성 : 한 줄씩 읽으므로 전체 파일 적재가 필요 없다.
  • 상태 보유 : 현재 파일 포인터 위치가 iterator 상태 역할을 수행한다.
  • 실전성 : 로그 분석과 대용량 처리에서 가장 대표적인 iterator 사례다.
$$\text{stream iteration} = \text{incremental I/O} + \text{protocol-conformant traversal}$$

  • 폐쇄성 : iterator를 입력받아 다시 iterator를 돌려주는 연산이 많다.
  • 지연 유지 : 중간 materialization 없이도 다단계 변환이 가능하다.
  • generator 연결 : 사용자 정의 조합 연산을 가장 간결하게 기술하는 수단이 generator다.
$$\text{iterator pipeline} = f_n \circ f_{n-1} \circ \cdots \circ f_1(\text{source iterator})$$

Part 18 · Transition

Generator는 iterator 구현 전략이다

Iterator를 클래스로 직접 구현하는 방식은 상태와 종료 규칙을 명시적으로 드러낸다. 그러나 상태 변수가 많아질수록 코드가 장황해진다. Generator는 동일한 protocol을 더 압축적으로 기술하는 수단이다.

Generator의 핵심은 다음 값의 계산과 중단 지점의 보존을 동시에 기술하는 데 있다. 따라서 generator는 값 생산 장치인 동시에 프레임 보존 장치로 해석된다.

  • 외부 관찰 : generator도 결국 iterator protocol을 만족하는 객체로 보인다.
  • 표현 차이 : class iterator는 상태를 직접 저장하고 generator는 프레임이 상태를 저장한다.
  • 선택 기준 : 상태가 단순하면 generator가, 다중 메서드 계약이 필요하면 class가 유리하다.
$$\text{generator} \subset \text{iterator implementations}$$
Generator는 iterator의 대체 개념이 아니라 iterator를 기술하는 함수형 표현이다. 외부 관찰 결과는 iterator protocol로 수렴한다.

Generator expression은 lazy comprehension이다

형식평가 시점메모리 특성

문법은 유사하지만 의미론은 다르다. list comprehension은 데이터를 즉시 materialize하고, generator expression은 필요 시점에 데이터를 생산한다. 이 차이는 메모리뿐 아니라 오류 발생 시점, 부수효과 시점, 디버깅 난이도까지 바꾼다.

  • 관측 차이 : 외부 상태 변화가 늦게 반영될 수 있어 결과 시점이 달라진다.
  • 사용 맥락 : 단일 패스 집계에는 generator가, 재사용과 디버깅에는 list가 더 유리할 수 있다.

Part 22 · Live Lab

배치 분할 generator 직접 구현

lazy batching은 generator의 대표적 사용처이다. 전체 데이터를 한꺼번에 들고 있지 않으면서도 소비자에게 일정한 배치 단위 인터페이스를 제공한다.

def chunked(iterable, size: int):
    bucket = []
    for item in iterable:
        bucket.append(item)
        if len(bucket) == size:
            yield bucket
            bucket = []
    if bucket:
        yield bucket


rows = [f"row-{i}" for i in range(1, 11)]
for batch in chunked(rows, 4):
    print(batch)

이 예시는 generator가 배열 생성 함수가 아니라 배치 생산 시점을 제어하는 실행 장치임을 드러낸다.

  • 배치 경계 : 소비자에게는 고정된 묶음 단위 인터페이스가 제공된다.
  • 메모리 제한 : 현재 bucket만 유지하므로 입력 전체 크기와 독립적이다.
  • 실무 연결 : 미니배치 학습과 블록 단위 처리에 직접 대응한다.
$$\text{chunked stream} = (x_1,\ldots,x_k), (x_{k+1},\ldots,x_{2k}), \ldots$$

def echo():

iterator는 보통 바깥에서 next()로 값을 꺼내는 구조로 소비된다. 그러나 generator는 send()를 통해 값 주입도 받을 수 있으며, 이때 단순 생산기를 넘어 양방향 상태 기계로 해석된다.

이 특성은 streaming statistics, coroutine, incremental parser, event-driven state machine 설계에 직접 연결된다.

  • 입력 채널 : yield 표현식은 출력 지점이면서 동시에 입력 수신 지점이 된다.
  • 상태 갱신 : 외부에서 주입된 값이 generator 내부 상태를 즉시 전이시킨다.
  • 코루틴 성격 : 값 생산기에서 상호작용적 상태 기계로 해석 범위가 넓어진다.
$$\texttt{send}(v):\ \text{resume generator with }(\texttt{yield expression} = v)$$

def running_average():
    total = 0.0
    count = 0
    avg = 0.0
    while True:
        x = yield avg
        if x is None:
            return avg
        total += x
        count += 1
        avg = total / count

print(g.send(10))
print(g.send(20))
print(g.send(30))

    g.send(None)
except StopIteration as e:

  • 온라인 계산 : 전체 데이터 저장 없이도 누적 통계를 갱신한다.

  • 상호작용성 : 매 입력마다 내부 상태가 갱신되는 계산 객체로 볼 수 있다.

Part 26 · Delegation

yield from은 루프 축약이 아니라 위임 메커니즘이다

def flatten(blocks):
    for block in blocks:
        yield from block
def sub():
    yield 1
    yield 2
    return "done"

def outer():
    result = yield from sub()
    yield result

yield from은 단순히 for x in sub: yield x의 줄임말이 아니다. 하위 generator의 send, throw, close, 그리고 종료값까지 위임한다. 따라서 recursive generator 구조를 정확하게 표현하는 데 적합하다.

  • 값 위임 : 하위 iterable이 생산한 값을 그대로 바깥으로 전달한다.
  • 제어 위임 : send, throw, close 같은 상호작용도 하위 generator로 전달된다.
  • 종료값 회수 : 하위 generator의 return value를 받아 상위 단계의 후속 로직에 사용할 수 있다.
$$\texttt{yield from }g \Rightarrow \text{delegate values} + \text{delegate control} + \text{collect return value}$$

  • 합성 가능성 : 상위 generator가 하위 계산 결과를 이어받아 후속 제어를 수행한다.
  • 파서 적합성 : 토큰 소비와 의미 결과 반환을 동시에 표현할 수 있다.

Part 28 · PEP 479

왜 generator 내부에서 새는 StopIteration은 위험한가

Generator 본문 안에서 의도치 않은 StopIteration이 조용한 종료로 해석되면 데이터 손실 버그가 은폐될 수 있다.

PEP 479 이후, generator 안에서 새는 StopIteration은 RuntimeError로 변환된다. 조용한 종료 대신 명시적 실패를 선택한 규칙이며, 재현성 요구가 높은 코드에서 특히 중요하다.

고급 Python에서는 명시적으로 실패하는 코드보다 조용히 잘못된 결과를 만드는 코드가 더 위험하다. iterator와 generator 관련 버그가 대표적 사례다.
  • 조용한 실패 방지 : 내부 실수를 정상 종료로 오인하지 않도록 한다.
  • 가시성 강화 : 오류가 runtime failure로 드러나 원인 추적이 쉬워진다.
  • 의미론 안정화 : 종료는 의도적 return 경로로만 표현되도록 규율한다.
$$\texttt{StopIteration leaking from generator body} \Rightarrow \texttt{RuntimeError}$$

Generator 기반 tokenizer

def tokenize(text: str):
    buf = []
    for ch in text:
        if ch.isalnum() or ch == "_":
            buf.append(ch)
        else:
            if buf:
                yield ("WORD", "".join(buf))
                buf.clear()
            if ch.strip():
                yield ("PUNC", ch)
    if buf:
        yield ("WORD", "".join(buf))


source = "alpha + beta_2 * gamma"

async for와 async generator는 “비동기 반복 프로토콜”이다

class AsyncCounter:
    def __init__(self, stop: int):
        self.current = 0
        self.stop = stop

    def __aiter__(self):
        return self

    async def __anext__(self):
        if self.current >= self.stop:
            raise StopAsyncIteration
        value = self.current
        self.current += 1
        return value

동기 iterator가 즉시 다음 값을 줄 수 있는가를 묻는다면, 비동기 iterator는 다음 값을 비동기적으로 기다려 받을 수 있는가를 묻는다. 프로토콜 구조는 유사하지만 제어권 반환이 event loop와 결합된다는 점이 다르다.

토큰 스트리밍, websocket 메시지 처리, 센서 이벤트 수집 같은 현대 시스템에서는 async iteration이 직접적인 분석 대상이 된다.

  • 프로토콜 확장 : __iter__/__next__가 __aiter__/__anext__로 치환된다.
  • event loop 결합 : 다음 값 계산이 비동기 스케줄링과 함께 이뤄진다.
  • 현대 시스템성 : 스트리밍과 네트워크 처리에서 핵심 반복 모델이다.
$$\text{async iteration} = \text{awaitable next item} + \texttt{StopAsyncIteration}$$

따라서 generator 설계에서는 값 생산 시점만이 아니라 종료 시점과 정리 정책까지 함께 기술되어야 한다.

  • 정확한 계약 : contextmanager generator는 정확히 한 번만 yield해야 한다.
  • 정리 우선성 : 생성보다 종료 시 정책이 더 중요해지는 대표 패턴이다.
$$\text{managed generator} = \text{setup} \rightarrow \text{yield exactly once} \rightarrow \text{cleanup}$$

  • 설계 원칙 : 순회 단계와 구조 변경 단계를 분리할수록 코드의 추론 가능성이 높아진다.

Part 38 · Comp vs Gen

List comprehension과 generator expression의 연결

xs = [x * x for x in range(10)]
ys = (x * x for x in range(10))

표면 문법은 유사하지만 의미론은 다르다. list comprehension은 전체 결과를 즉시 계산하여 저장하고, generator expression은 소비 요청이 발생할 때마다 값을 산출한다. 따라서 차이는 메모리 사용량에 그치지 않고 부수효과 시점과 예외 노출 시점까지 바꾼다.

입력 데이터가 외부 상태에 의존한다면 generator expression은 소비 시점의 상태를 반영하고, list comprehension은 생성 시점의 상태를 고정한다. 이 차이는 재현성, 캐싱 전략, 디버깅 절차를 직접 규정한다.

  • 시점 차이 : 생성 시점과 소비 시점이 분리되면 관찰 결과가 달라질 수 있다.
  • 부수효과 차이 : 함수 호출과 예외 발생 시점도 eager/lazy 여부에 따라 이동한다.
  • 문법 유사성 한계 : 표면이 비슷해도 실행 의미론은 크게 다르다.
$$[\phi(x)\ \text{for}\ x\in X] = \text{eager materialization},\qquad (\phi(x)\ \text{for}\ x\in X) = \text{lazy production}$$

deque

    if x % 2 == 0
)

print(list(pipeline))

이 예제는 생성, 필터링, 변환이 모두 lazy하게 연결되고 마지막 list()가 결과를 고정하는 전형적 구조를 보인다. 데이터 처리 파이프라인에서 eager boundary가 어디에 놓이는지 관찰하기에 적합하다.

결과를 한 번만 소비할 예정이라면 list는 생략 가능하다. 반대로 결과를 여러 번 사용하거나 정렬, 길이 측정, 디버깅, 테스트가 필요하다면 materialization이 설계상 합리적 선택이 된다.

  • lazy chain : source, filter, map 단계는 소비 전까지 실제 계산을 지연시킨다.
  • boundary placement : 마지막 list() 위치가 설계상 중요한 결정이다.
  • 재사용성 전환 : materialization 이후에는 동일 결과를 여러 연산이 공유할 수 있다.
$$\text{result} = \texttt{list}\big(\text{map} \circ \text{filter} \circ \text{source}\big)$$
Part 45 · Replay

List는 replay와 caching을 위한 효과적인 경계가 된다

iterator와 generator는 흐름 표현에 적합하지만, 이미 소비한 값을 재현하기 어렵다. list는 이 문제를 해결하는 가장 단순한 replay boundary로 기능한다.

expensive generator를 한 번 실행해 list로 저장하면 여러 분석 단계가 동일한 결과를 재사용할 수 있다. 다만 입력 규모가 커질수록 memory pressure가 증가하고 streaming의 장점은 감소한다.

따라서 list는 단순 저장소라기보다, 재사용성·디버깅 가능성·재현성을 위해 의도적으로 도입하는 캐시 경계로 해석되어야 한다.

  • replay : 이미 지나간 값을 다시 관찰할 수 있게 만든다.
  • cache boundary : 비싼 전처리 결과를 여러 분석기가 공유하는 지점이 된다.
  • trade-off : 메모리 사용 증가와 스트리밍 장점 상실을 함께 감수해야 한다.
$$\text{replayability} = \text{materialized snapshot of a lazy source}$$

Part 51 · Live Lab

내부적으로 generator를 쓰는 iterable class

class WindowedReadings:
    def __init__(self, readings, window_size: int):
        if window_size <= 0:
            raise ValueError("window_size must be positive")
        self.readings = list(readings)
        self.window_size = window_size

    def __repr__(self):
        return f"WindowedReadings(n={len(self.readings)}, window={self.window_size})"

    def __iter__(self):
        for i in range(0, len(self.readings) - self.window_size + 1):
            yield self.readings[i:i + self.window_size]


wr = WindowedReadings([3, 5, 8, 13, 21], 3)
print(wr)
print(list(wr))
print(list(wr))

  • 내부 전략 : 실제 순회 상태는 generator frame이 유지한다.

$$\text{public iterable} = \text{class interface} + \text{generator-backed traversal}$$
Part 52 · Descriptor

Descriptor는 클래스 모델의 핵심 축이다

class Descriptor:
    def __get__(self, obj, objtype=None): ...
    def __set__(self, obj, value): ...
    def __delete__(self, obj): ...

Python의 메서드 바인딩, property, classmethod, staticmethod는 모두 descriptor 메커니즘 위에 놓여 있다. 따라서 descriptor는 class 모델의 주변 기능이 아니라 속성 의미론의 핵심 축에 해당한다.

descriptor의 본질은 속성 접근을 객체화하는 데 있다. 값 조회만 수행하는 대신, 읽기와 쓰기, 삭제라는 행위 자체를 정책 지점으로 바꾸어 검증, 계산, 바인딩, 캐싱을 삽입할 수 있다.

  • data descriptor : __set__ 또는 __delete__를 포함하여 instance dictionary보다 높은 우선순위를 갖는다.
  • non-data descriptor : 함수 객체처럼 __get__만 구현하여 바인딩 의미론을 제공한다.
  • 핵심 가치 : 속성 접근을 단순 조회가 아니라 정책 적용 지점으로 전환한다.
$$\text{attribute access} = \text{lookup order} + \text{binding policy} + \text{side-effect control}$$

__set_name__을 활용한 검증 descriptor

class PositiveFloat:
    def __set_name__(self, owner, name):
        self.private_name = "_" + name

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self
        return getattr(obj, self.private_name)

    def __set__(self, obj, value):
        value = float(value)
        if value <= 0:
            raise ValueError("value must be positive")
        setattr(obj, self.private_name, value)


class OptimConfig:
    lr = PositiveFloat()

    def __init__(self, lr):
        self.lr = lr


cfg = OptimConfig(0.01)
print(cfg.lr)
cfg.lr = 0.1
print(cfg.lr)

  • __set_name__ : 필드 이름을 자동 수집하여 private storage와 결합한다.

  • 실무 연결 : ORM, serializer, config schema는 이 메커니즘을 핵심적으로 활용한다.

        self.value = value

고급 Python에서 class는 런타임 객체이면서 동시에 타입 시스템의 표면이기도 하다. Box[int] 같은 표현은 단순 표기법이 아니라 generic contract를 문서화하고 정적 분석 도구가 이해할 수 있게 만드는 장치다.

__class_getitem__를 직접 구현할 수도 있지만, 대부분의 상황에서는 typing.Generic 기반 설계로 충분하다. 핵심은 타입 힌트가 구현 보조물이 아니라 설계 문서 역할을 수행한다는 점이다.

  • generic class : 동일한 구조를 여러 타입 인자에 대해 안전하게 재사용하게 한다.
  • __class_getitem__ : Cls[T] 문법을 런타임에서도 해석하는 훅이다.
  • 설계 가치 : 타입 힌트는 검사기 입력이면서 동시에 협업용 API 문서다.
$$\text{Generic class} = \text{shape invariant} + \text{type parameterization}$$
Part 59 · MRO

다중 상속은 결국 C3 linearization 문제다

class A: ...
class B(A): ...
class C(A): ...
class D(B, C): ...

print(D.__mro__)

다중 상속이 어려운 이유는 부모 수가 많기 때문이 아니라, 탐색 순서를 일관되게 정해야 하기 때문이다. Python은 C3 linearization을 사용해 지역 우선 순서와 단조성을 동시에 보존한다.

descriptor lookup, 메서드 호출, super() 협력은 모두 MRO에 의존한다. 따라서 다중 상속은 문법 문제가 아니라 선형화 문제로 이해되어야 한다.

  • local precedence : 자식이 명시한 부모 순서를 가능한 한 보존한다.
  • monotonicity : 상위 클래스의 우선순위 관계가 하위 클래스에서 뒤집히지 않도록 한다.
  • 실무 의미 : mixin 체인과 super() 협력이 유지되도록 만드는 기반이다.
$$MRO(C) = [C] + \mathrm{merge}(MRO(B_1), \ldots, MRO(B_n), [B_1,\ldots,B_n])$$
Part 60 · super()

협력적 다중 상속은 모두가 super()를 지킬 때만 성립한다

class LoggingMixin:
    def process(self, x):
        print("log", x)
        return super().process(x)

class NormalizeMixin:
    def process(self, x):
        x = x.strip().lower()
        return super().process(x)

class BaseProcessor:
    def process(self, x):
        return x

super()는 부모 클래스 직접 호출 문법이 아니라, 현재 MRO에서 다음 후보를 호출하는 협력 장치다. 따라서 mixin과 다중 상속이 존재하는 설계에서는 모든 참여자가 동일한 규약을 따라야 한다.

하나의 클래스라도 특정 부모를 직접 호출하면 선형화 계약이 깨질 수 있다. 다중 상속 코드가 취약해지는 이유는 다수 상속 자체가 아니라 협력 규약의 붕괴에 있다.

  • 직접 부모 호출 금지 : 특정 부모명을 고정하면 다른 mixin이 체인에서 누락될 수 있다.
  • 시그니처 협력 : 여러 클래스가 동일한 호출 체인을 공유하므로 인자 계약도 협력적으로 설계되어야 한다.
  • 정확한 해석 : super()는 부모가 아니라 현재 MRO의 다음 후보를 의미한다.
$$\texttt{super()} = \text{next dispatch target in } MRO(\text{current class}, \text{instance})$$
Part 61 · Pattern Matching

Class pattern matching은 구조적 분해 도구다

from dataclasses import dataclass

@dataclass
class Token:
    kind: str
    value: str

def classify(tok: Token) -> str:
    match tok:
        case Token("INT", v):
            return f"integer:{v}"
        case Token("ID", v):
            return f"identifier:{v}"
        case _:
            return "other"

pattern matching은 class를 단순 객체가 아니라 분해 가능한 구조로 취급한다. AST 처리, 파서, 이벤트 분기 로직에서는 복잡한 if/elif 체인을 선언적 분해 규칙으로 치환할 수 있다.

다만 구조가 명확하지 않은 문제에 과도하게 적용하면 코드가 기호적으로 과밀해질 수 있다. 따라서 구조적 분해가 의미론적으로 분명한 경우에 사용하는 것이 적절하다.

  • 분기 가독성 : 토큰 종류나 AST 노드 타입에 따른 분기를 선언적으로 기술한다.
  • 데이터 모델 연결 : dataclass나 tuple-like object와 특히 잘 결합된다.
  • 주의점 : 미세한 제어 로직까지 pattern으로 밀어 넣으면 가독성이 저하된다.
$$\text{class match} = \text{constructor tag} + \text{field decomposition} + \text{optional guard}$$
Part 62 · Subclass Hooks

__init_subclass__는 metaclass보다 가벼운 확장점이다

class PluginBase:
    registry = {}

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        if cls.__name__ != "PluginBase":
            PluginBase.registry[cls.__name__] = cls

__init_subclass__는 하위 클래스 정의가 완료될 때마다 호출된다. 자동 등록, 정책 검사, 공통 옵션 주입 같은 작업을 metaclass 없이 처리할 수 있으므로 실용적 확장점으로 기능한다.

클래스 정의 시점에 정책을 적용하고 싶다면 우선 이 훅으로 충분한지 평가하는 것이 바람직하다. metaclass는 더 강력하지만 범위와 침투성이 훨씬 크다.

  • plugin registry : 전략 객체 자동 등록 패턴에 적합하다.
  • 정의 시점 검증 : 하위 클래스의 필수 속성과 메서드 존재를 즉시 검사할 수 있다.
  • 경량 훅 : metaclass보다 적용 범위가 좁고 유지보수 부담이 낮다.
$$\text{subclass registration} = \text{class definition event} \rightarrow \text{policy hook}$$
Part 63 · Metaclass

Metaclass는 “클래스를 만드는 클래스”라는 설명만으로는 부족하다

class RegistryMeta(type):
    registry = {}

    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, ns)
        if name != "Plugin":
            mcls.registry[name] = cls
        return cls

metaclass의 핵심 의미는 클래스 정의 시점의 파이프라인에 개입할 수 있다는 데 있다. namespace 변경, 클래스 검증, 자동 등록, 문법 수준 DSL 구축이 모두 이 층에서 가능하다.

그러나 그만큼 읽기 난도가 높아지고 도구 친화성도 저하될 수 있다. descriptor, decorator, __init_subclass__로 해결 가능한 문제라면 metaclass 사용은 보류하는 편이 타당하다.

  • 정의 시점 개입 : 클래스 생성 순간에 규약을 강제한다.
  • DSL 가능성 : ORM, serializer, config schema 같은 도메인 언어가 이 수준 훅을 활용한다.
  • 비용 : 강력하지만 팀 전체의 추론 난도를 높이므로 마지막 수단에 가깝다.
$$\text{metaclass power} = \text{namespace control} + \text{class construction control}$$
Part 64 · Equality & Hash

__eq__, __hash__, 불변성 계약은 객체 모델의 안전장치다

from dataclasses import dataclass

@dataclass(frozen=True)
class Key:
    run_id: str
    seed: int


scores = {Key("exp-1", 42): 0.91}
print(scores[Key("exp-1", 42)])

객체를 dict key나 set 원소로 사용하려면 동등성과 해시가 일관적이어야 한다. 이 계약은 클래스 설계의 안전장치이며, 캐시, memoization, 결과 조회, 중복 제거 같은 고급 기능의 기반을 이룬다.

  • 핵심 법칙 : a == b이면 반드시 hash(a) == hash(b)가 성립해야 한다.
  • 불변성 요구 : hash 참여 필드가 바뀌면 dict/set 내부 인덱싱이 붕괴할 수 있다.
  • 실무 권장 : 직접 __hash__를 작성하기보다 frozen dataclass를 우선 고려하는 편이 안전하다.
$$a = b \Rightarrow h(a) = h(b),\qquad \text{mutable hash fields} \Rightarrow \text{index instability}$$
박사 수준 연구 코드에서 설정 객체를 mutable한 채 key로 사용하는 설계는 매우 위험하다. 캐시 적중 실패나 조회 오류가 조용히 발생할 수 있다.
Part 65 · Callable Object

__call__은 클래스를 “상태를 가진 함수”로 바꾼다

class TemperatureScaler:
    def __init__(self, temperature: float):
        self.temperature = temperature

    def __call__(self, logit: float) -> float:
        return logit / self.temperature


scale = TemperatureScaler(0.7)
print(scale(3.5))

callable object는 함수형 인터페이스와 객체 상태를 결합해야 하는 상황에서 강력한 설계 도구가 된다. scoring rule, decoding policy, transform operator, callback object는 모두 __call__과 잘 결합되는 전형적 사례다.

  • 상태 결합 : 반복적으로 넘기던 파라미터를 객체 상태로 캡슐화할 수 있다.
  • 파이프라인 적합성 : iterator/generator pipeline 단계를 callable object로 모델링할 수 있다.
  • 확장성 : 호출 이력 기록, 내부 캐시, 통계 수집을 자연스럽게 통합할 수 있다.
$$\text{callable object} = \text{function interface} + \text{encapsulated state} + \text{call-time policy}$$
Part 66 · Context Classes

__enter__, __exit__를 구현하면 클래스가 수명 주기를 관리한다

class Timer:
    def __enter__(self):
        import time
        self._clock = time.perf_counter
        self.start = self._clock()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.elapsed = self._clock() - self.start
        return False

class는 단순 데이터 구조에 머물지 않고 lifecycle abstraction이 될 수 있다. context manager class는 자원 획득과 해제를 객체 불변식으로 묶기 때문에, 상태가 복잡한 경우에는 generator 기반 context manager보다 더 명시적인 구조를 제공한다.

  • 자원 관리 : 파일, 락, 트랜잭션, 프로파일링 세션을 안전하게 감싼다.
  • 예외 정책 : __exit__ 반환값으로 예외 삼킴 여부를 결정한다.
  • 설계 메시지 : 클래스는 데이터뿐 아니라 시작-사용-정리 경계를 표현할 수 있다.
$$\text{context class} = \text{enter} \rightarrow \text{use} \rightarrow \text{exit}$$
Part 67 · Rare Hooks

박사 수준에서 알아둘 class-level 희귀 훅들

class Meta(type):
    @classmethod
    def __prepare__(mcls, name, bases):
        return {}

class FancyBase:
    def __mro_entries__(self, bases):
        return ()

    def __class_getitem__(cls, item):
        return (cls, item)

이 훅들은 빈번히 사용되지는 않지만 Python 클래스 모델의 확장 경계를 드러낸다. 프레임워크나 DSL이 언어 수준 구조처럼 보이는 이유도 상당 부분 이런 훅들의 존재에 있다.

  • __prepare__ : 클래스 본문 실행 전 namespace를 교체하여 정의 순서와 특수 매핑을 제어한다.
  • __mro_entries__ : 동적 기반 클래스 적응이나 가상 상속 계층 구성에 개입한다.
  • __class_getitem__ : Cls[T] 문법을 런타임에서도 해석하게 한다.
이 훅들의 가치는 일상적 사용 빈도보다 Python 객체 모델의 표현 한계를 정밀하게 이해하는 데 있다.
$$\text{class extensibility} = \text{definition-time hooks} + \text{resolution hooks} + \text{typing hooks}$$
Part 68 · Slots

__slots__는 단순 메모리 최적화가 아니라 인스턴스 레이아웃 선언이다

class Sample:
    __slots__ = ("step", "loss", "__weakref__")

    def __init__(self, step: int, loss: float):
        self.step = step
        self.loss = loss

__slots__는 인스턴스가 가질 수 있는 저장 위치를 클래스 정의 시점에 선언한다. 이 선언은 단순 성능 팁이 아니라, 인스턴스 사전의 존재 여부와 동적 속성 추가 가능성, weak reference 지원 여부까지 규정하는 레이아웃 계약이다.

클래스 생성 시 각 slot 이름은 member descriptor로 변환된다. 따라서 __slots__는 메모리 절약 기법인 동시에 descriptor 기반 저장 모델을 생성하는 문법이기도 하다.

  • member descriptor 생성 : slot 이름마다 클래스 수준 descriptor가 생성되어 저장 위치를 관리한다.
  • 동적 속성 통제 : 기본적으로 __dict__가 제거되므로 임의 속성 추가가 차단된다.
  • 상속 주의점 : 다중 상속에서는 레이아웃 충돌과 __weakref__ 포함 여부를 함께 고려해야 한다.
$$\text{instance layout} = \text{slot descriptors} + \text{optional } \_\_dict\_\_ + \text{optional } \_\_weakref\_\_$$
Part 69 · Attribute Control

__setattr__와 __delattr__는 상태 전이 정책을 장악한다

class Probability:
    __slots__ = ("value",)

    def __setattr__(self, name, value):
        if name == "value" and not (0.0 <= value <= 1.0):
            raise ValueError("probability must be in [0, 1]")
        object.__setattr__(self, name, value)

속성 쓰기는 단순 저장 동작이 아니라 객체 불변식이 통과해야 하는 상태 전이로 해석되어야 한다. __setattr__와 __delattr__는 이 전이 경로를 제어하는 중앙 훅이며, validator, proxy, frozen object emulation, audit logging이 모두 이 층과 연결된다.

이 훅을 재정의할 때는 재귀를 피하기 위해 반드시 object.__setattr__ 또는 상위 구현으로 위임해야 한다. 그렇지 않으면 쓰기 경로가 자기 자신을 무한 호출하게 된다.

  • 불변식 집행 : 범위 제한, 상태 머신 전이 규칙, 접근 감사 정책을 한 곳에 모을 수 있다.
  • 재귀 회피 : 커스텀 훅 내부에서 일반 대입문을 사용하면 무한 재귀가 발생할 수 있다.
  • 설계 해석 : 읽기 경로의 descriptor와 쓰기 경로의 __setattr__를 결합하면 강한 객체 정책을 만들 수 있다.
$$\text{attribute write} = \text{validation} + \text{storage routing} + \text{invariant preservation}$$
Part 70 · Class Cell

zero-argument super() 뒤에는 __classcell__이 존재한다

class Base:
    def describe(self):
        return "base"

class Child(Base):
    def describe(self):
        return super().describe() + " -> child"

zero-argument super()는 문법적 축약에 그치지 않는다. 컴파일러는 해당 메서드 안에 숨은 __class__ cell을 주입하고, 런타임은 이를 이용해 현재 클래스와 첫 번째 인자를 바탕으로 다음 MRO 후보를 계산한다.

메타클래스가 클래스 생성을 깊게 커스터마이즈할 때는 __classcell__ 전달이 깨지지 않도록 주의해야 한다. 이 세부를 놓치면 협력적 super()가 런타임 오류를 일으킬 수 있다.

  • 컴파일러 개입 : 메서드가 super() 또는 __class__를 사용하면 클래스 cell이 생성된다.
  • 메타클래스 책임 : 커스텀 클래스 생성 파이프라인은 __classcell__를 보존해야 한다.
  • 의미론 : zero-argument super()는 클래스 본문과 클로저 의미론까지 포함하는 고급 문법이다.
$$\texttt{super()} \equiv \texttt{super}(\_\_class\_\_, \text{first argument})$$
Part 71 · Virtual Subtyping

ABCMeta.register와 __subclasshook__는 가상 서브클래스를 정의한다

from abc import ABCMeta, abstractmethod

class Reader(metaclass=ABCMeta):
    @abstractmethod
    def read(self, n: int = -1) -> str: ...

    @classmethod
    def __subclasshook__(cls, C):
        if any("read" in B.__dict__ for B in C.__mro__):
            return True
        return NotImplemented

가상 서브클래싱은 상속 계층을 실제로 수정하지 않으면서 런타임 계약 멤버십을 조정하는 메커니즘이다. 즉, issubclass 결과와 실제 MRO 포함 관계를 분리할 수 있다.

이 기능은 어댑터 패턴이나 오래된 타입을 새 계약에 편입할 때 유용하지만, 메서드 구현을 자동으로 주입하지는 않는다. 따라서 구조 호환성과 의미 호환성을 동시에 만족하는 경우에만 사용해야 한다.

  • 계약 멤버십 : nominal inheritance 없이도 런타임 계약 판정을 조정할 수 있다.
  • MRO 비개입 : 가상 서브클래스는 메서드 탐색 순서나 메모리 레이아웃을 바꾸지 않는다.
  • 정적 분석 차이 : 런타임 적응과 정적 타입 시스템의 판단이 다를 수 있음을 명시적으로 인식해야 한다.
$$\texttt{issubclass}(C, A)=\texttt{True} \not\Rightarrow A \in MRO(C)$$
Part 72 · Advanced Typing

Self, variance, generic method는 class API의 타입 보존성을 다룬다

from typing import Generic, Self, TypeVar

T_co = TypeVar("T_co", covariant=True)

class FrozenBox(Generic[T_co]):
    def __init__(self, value: T_co):
        self._value = value

    def get(self) -> T_co:
        return self._value

class Builder:
    def clone(self) -> Self:
        return type(self)()

고급 class 설계에서는 런타임 상속 구조와 정적 대체 가능성 규칙을 함께 맞추어야 한다. 읽기 전용 추상화는 공변적으로 모델링할 수 있지만, 쓰기 가능한 컨테이너는 대개 불변(invariant)하게 유지해야 안전하다.

Self는 메서드가 정확히 현재 동적 클래스의 인스턴스를 반환함을 표현한다. 이 표기는 fluent API, builder, clone, 대체 생성자 설계에서 하위 클래스 정밀도를 유지하는 핵심 도구다.

  • variance 선택 : 타입 매개변수는 읽기/쓰기 가능성에 따라 공변, 반공변, 불변이 결정된다.
  • Self : 상속된 메서드 체인에서 반환 타입 정밀도를 유지한다.
  • 설계 원리 : generic class는 값 타입뿐 아니라 대체 가능성 법칙까지 문서화해야 한다.
$$A \le B \Rightarrow \text{ReadOnly}[A] \le \text{ReadOnly}[B],\qquad \text{mutable containers are typically invariant}$$
Part 73 · Metaclass Conflict

다중 상속에서는 metaclass도 합성 가능해야 한다

class MetaA(type): ...
class MetaB(type): ...

class A(metaclass=MetaA): ...
class B(metaclass=MetaB): ...

# class C(A, B): ...   # TypeError

class MetaAB(MetaA, MetaB): ...
class C(A, B, metaclass=MetaAB): ...

다중 상속의 제약은 클래스 계층에만 적용되지 않는다. 새 클래스의 metaclass는 모든 기반 클래스 metaclass의 공통 하위 타입이어야 하며, 그렇지 않으면 클래스 생성 자체가 거부된다.

프레임워크를 조합할 때 발생하는 metaclass conflict는 이차적인 선형화 문제다. 따라서 metaclass 설계는 기능 추가보다 조합 가능성을 우선 고려해야 한다.

  • 합성 제약 : 기반 클래스의 metaclass들을 동시에 만족하는 파생 metaclass가 필요하다.
  • 실무 위험 : 서로 다른 라이브러리의 base class를 단순 조합하는 순간 충돌이 드러날 수 있다.
  • 회피 전략 : descriptor, decorator, __init_subclass__로 충분하면 metaclass 사용을 줄이는 편이 안전하다.
$$\forall i,\ \texttt{issubclass}(\mathrm{Meta}(C), \mathrm{Meta}(B_i))$$
Part 74 · Reflective Surface

__annotations__, __match_args__, inspect는 class의 반사 표면을 형성한다

class Point:
    __match_args__ = ("x", "y")
    x: float
    y: float

    def __init__(self, x: float, y: float):
        self.x = x
        self.y = y

현대 Python 프레임워크는 객체가 수행하는 메서드만 읽지 않는다. 클래스 본문에 남겨진 annotation, descriptor, pattern metadata, call signature를 조합해 검증기, serializer, ORM, dependency injection 도구를 구성한다.

이 관점에서 class는 단순 실행 단위가 아니라 선언적 schema surface이기도 하다. 즉, 반사 가능한 메타데이터의 품질이 곧 도구 생태계와의 결합 품질을 결정한다.

  • __annotations__ : 타입 힌트를 넘어 도메인 스키마 정보를 제공한다.
  • __match_args__ : class pattern matching의 위치 기반 분해 순서를 제어한다.
  • 반사 도구 : inspect, serializer, validator는 이 메타데이터 표면을 읽어 동작한다.
$$\text{reflective class surface} = \text{annotations} + \text{descriptors} + \text{match metadata} + \text{call signature}$$
Part 75 · Framework Pattern

실제 프레임워크는 descriptor, annotation, subclass hook를 조합한다

class Field:
    def __init__(self, cast):
        self.cast = cast

    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self
        return obj.__dict__[self.name]

    def __set__(self, obj, value):
        obj.__dict__[self.name] = self.cast(value)

class Schema:
    def __init_subclass__(cls):
        super().__init_subclass__()
        cls.fields = {
            name: attr for name, attr in cls.__dict__.items()
            if isinstance(attr, Field)
        }

ORM, validation library, configuration system, experiment tracking framework는 보통 하나의 마법 훅으로 만들어지지 않는다. descriptor가 필드 정책을 담당하고, annotation이 스키마를 제공하며, subclass hook 또는 metaclass가 정의 시점 등록을 수행하는 식의 조합 구조가 일반적이다.

박사 수준에서 class 문법을 이해한다는 것은 개별 dunder 이름을 암기하는 일이 아니라, 이 훅들을 조합해 도메인 언어와 런타임 계약을 설계할 수 있다는 뜻에 가깝다.

  • 필드 정책 : descriptor가 개별 속성의 검증과 저장 규칙을 담당한다.
  • 정의 시점 수집 : subclass hook이나 metaclass가 스키마 레지스트리를 만든다.
  • 프레임워크 해석 : class body는 선언적 DSL, instance는 실행 객체로 분업된다.
$$\text{framework class DSL} = \text{annotated namespace} + \text{descriptor semantics} + \text{definition-time registration}$$
Part 76 · Integrated Case

모든 것을 합친 사례: stream analytics architecture

raw lines (iterator)
  -> tokenize (generator)
  -> parse into dataclass records
  -> optional list materialization for replay
  -> analyzer class exposing metrics API

각 요소의 역할

iterator는 데이터 접근 계약을 표준화하고, generator는 변환 파이프라인을 만들며, list는 필요 시 결과를 고정하고, class는 이를 안정적인 API와 불변식으로 조직한다.

왜 이 구조가 강한가

입력이 작을 때는 list 중심, 입력이 클 때는 generator 중심, 도메인 정책은 class 중심으로 조정할 수 있으므로 규모 변화와 요구 변화에 모두 견고하다.

이 구조는 강의 전체의 요약이기도 하다. 네 개의 주제는 분리된 문법 항목이 아니라 하나의 Python 설계 스택을 구성한다.

  • 입력 층 : iterator는 데이터 접근 경로를 표준화해 다양한 소스를 같은 방식으로 연결한다.
  • 변환 층 : generator는 토큰화, 필터링, 파싱 같은 중간 계산을 지연 파이프라인으로 조직한다.
  • 고정과 API 층 : list는 재사용 가능한 값 표면을 만들고 class는 이를 안정적 도메인 API로 묶는다.
$$\text{system pipeline} = \text{iterator source} \rightarrow \text{generator transform} \rightarrow \text{list boundary} \rightarrow \text{class API}$$
Part 77 · Final Heuristics

최종 설계 휴리스틱과 과제 제안

휴리스틱 1 : 데이터를 저장하는 방식보다 생산과 소비 방식이 우선이면 iterator/generator 모델이 먼저 고려되어야 한다.
휴리스틱 2 : 재사용, 디버깅, 정렬, 길이, 랜덤 접근이 핵심 요구가 되는 순간 list materialization이 설계 경계가 된다.
휴리스틱 3 : 프로토콜과 정책을 외부 API로 안정화해야 할 때 class가 도입되어야 한다.
휴리스틱 4 : 필드 수준 정책은 descriptor/property, 클래스 정의 시점 정책은 __init_subclass__, 마지막 단계에서만 metaclass를 사용한다.
과제 구성: 1) JSONL 로그 스트림을 읽는 iterable class 구현, 2) rolling median generator 구현, 3) dataclass와 descriptor를 결합한 실험 설정 모델 설계, 4) lazy pipeline과 list materialization 지점을 바꾸어 성능과 재현성 차이를 분석.

iterator는 접근 계약, generator는 실행 전략, list는 eager boundary, class는 이들을 시스템 수준 API와 정책으로 통합하는 구조다. 이 네 층을 함께 이해할 때 Python은 단순 구현 언어를 넘어 설계 언어로 기능한다.

  • 프로토콜 우선 : 순회와 접근 계약을 먼저 정의하면 이후 구현 선택이 선명해진다.
  • 경계 명시 : eager materialization 지점은 성능과 재현성을 동시에 좌우한다.
  • 객체 모델 통합 : class는 상태, 정책, reflection, metaprogramming을 한 자리에서 조직하는 최종 추상화다.
$$\text{Python design stack} = \text{protocol} + \text{execution strategy} + \text{materialization boundary} + \text{object abstraction}$$
